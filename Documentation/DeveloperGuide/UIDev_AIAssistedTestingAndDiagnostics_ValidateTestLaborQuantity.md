# AI-Assisted Testing and Diagnostics with Test SDK: To Validate the AI-Generated UI Test

This activity will walk you through the process of reviewing and validating the labor quantity UI test.

## Story

Suppose that Copilot has generated a UI test for the labor quantity validation scenario. The test looks plausible, but UI automation tests can fail for many reasons: wrapper mismatch, missing test data, timing issues, validation not being triggered, or a real application behavior problem.

In this activity, you'll review the generated test, run it, review the successful test output, review a prepared failure artifact, and use Copilot to classify the failure.

## Process Overview

You'll validate the UI test by performing the following steps:

1.  Reviewing the test runner setup
2.  Running the smoke test
3.  Running the labor quantity validation test
4.  Reviewing the passing output
5.  Reviewing a prepared failure artifact
6.  Asking Copilot to classify the failure

## System Preparation

Before you begin performing the steps of this activity, do the following

1.  Complete the [AI-Assisted Testing and Diagnostics with Test SDK: To Generate a UI Test for Labor Quantity Validation](UIDev_AIAssistedTestingAndDiagnostics_GenerateTestQuantityValidation.md) prerequisite activity.
2.  Make sure the `AIAssistedDiagnostics.ModernUI.Tests` project builds successfully.
3.  Make sure the target Acumatica ERP instance is running.
4.  Confirm that the Test SDK `config.xml` points to the correct site.
5.  Make sure the Test SDK user can sign in and open the Repair Work Orders \(RS301000\) form in the instance.
6.  Make sure the repair work order *000001* exists and has a labor line with the default quantity, *1*.
7.  Open the following files in Visual Studio:
    -   `Tests\StartTests.cs`
    -   `Tests\RS301000_LaborQuantityTests.cs`
    -   `Wrappers\Custom\RepairWorkOrdersScreen.cs`
    -   `Helpers\TestData.cs`
8.  Make sure the prepared passing and failure artifacts are available:
    -   `artifacts\passing\modern-ui-testsdk-passing-output.txt`
    -   `artifacts\failures\wrapper-member-not-found-output.txt`
    -   `artifacts\failures\validation-not-triggered-output.txt`
    -   `artifacts\failures\test-data-not-found-output.txt`
    -   `artifacts\failures\timing-wait-timeout-output.txt`
    -   `artifacts\failures\environment-config-error-output.txt`

## Step 1: Reviewing the Test Runner Setup

In this step, you'll confirm that the Test SDK runner is configured to run only the prepared smoke test and the UI test for the labor quantity validation, which you generated by using Copilot in the [AI-Assisted Testing and Diagnostics with Test SDK: To Generate a UI Test for Labor Quantity Validation](UIDev_AIAssistedTestingAndDiagnostics_GenerateTestQuantityValidation.md) prerequisite activity.

Do the following:

1.  Open `StartTests.cs` file.
2.  Confirm that the RS301000 smoke test is called \(shown below\).

    ```csharp
    using (TestExecution.CreateTestStepGroup("RS301000 smoke test"))
     {
         Console.WriteLine("Starting RS301000 smoke test...");
    
         var rs301000Tests = new RS301000_LaborQuantityTests();
         rs301000Tests.RepairWorkOrdersScreen_CanOpenPreparedWorkOrder();
     }
    ```

3.  Add the code to call the UI test for the labor quantity validation after the code in the preceding instruction. The following code shows an example.

    ```csharp
    using (TestExecution.CreateTestStepGroup("RS301000 labor quantity validation test"))
    {
        Console.WriteLine("Starting RS301000 labor quantity validation test...");
    
        var rs301000Tests = new RS301000_LaborQuantityTests();
        rs301000Tests.LaborQuantity_WhenBelowConfigured_RestoresConfiguredQuantity();
    
    }
    ```


## Step 2: Running the Smoke Test

In this step, you'll validate that the project can open the Repair Work Orders \(RS301000\) form and the prepared record. Do the following:

1.  In `StartTests.cs`, run only the smoke test first. You can temporarily comment out the line that runs the UI test for the labor quantity validation, which you added in Instruction 3 of the previous step.
2.  Build the `AIAssistedDiagnostics.ModernUI.Tests` project.
3.  Start the `AIAssistedDiagnostics.ModernUI.Tests` project by clicking **Debug** &gt; **Start Debugging** in Visual Studio.
4.  Confirm that:
    -   The browser opens and signs in to your configured Acumatica ERP site.
    -   The test opens the Repair Work Orders form.
    -   The test opens or selects the *000001* repair work order.
    -   The smoke test completes successfully.
5.  If the smoke test fails, stop and review the newest Test SDK log before running the validation test.

The passing smoke test flow:

-   Opens the Repair Work Orders form and waits for it to load
-   Types *000001* into the **Order Nbr.** box
-   Gets the current **Quantity** value from the single line item added in the table on the **Labor** tab of the form

## Step 3: Running the UI Test for the Labor Quantity Validation

In this step, you'll validate the UI test that Copilot helped you write for the labor quantity validation scenario. Do the following:

1.  Enable the UI test for the labor quantity validation in `StartTests.cs`. \(You commented it out in Instruction 1 of the previous step.\)
2.  Verify that the contents of the `StartTests.cs` file look similar to the following code.

    ```csharp
    using System;
    using AIAssistedDiagnostics.ModernUI.Tests.Tests;
    using Core.Login;
    using Core.TestExecution;
    
    namespace GeneratedWrappers.SOLUTIONNAME
    {
      internal class StartTests
      {
          public void Execute()
          {
              PxLogin.LoginToDestinationSite();
    
              using (TestExecution.CreateTestStepGroup("RS301000 smoke test"))
              {
                  Console.WriteLine("Starting RS301000 smoke test...");
    
                  var rs301000Tests = new RS301000_LaborQuantityTests();
                  rs301000Tests.RepairWorkOrdersScreen_CanOpenPreparedWorkOrder();
              }
    
              // Run the test that verifies that the labor quantity is restored 
              // after setting it below the configured value.
              using (TestExecution.CreateTestStepGroup
                     ("RS301000 labor quantity validation test"))
              {
                   Console.WriteLine
                   ("Starting RS301000 labor quantity validation test...");
    
                  var rs301000Tests = new RS301000_LaborQuantityTests();
                  rs301000Tests.LaborQuantity_WhenBelowConfigured_RestoresConfiguredQuantity();
    
              }
          }
      }
    }
    ```

3.  Build the `AIAssistedDiagnostics.ModernUI.Tests` project.
4.  Start the `AIAssistedDiagnostics.ModernUI.Tests` project by clicking **Debug** &gt; **Start Debugging** in Visual Studio.
5.  Confirm that:
    -   The browser opens and signs in to your configured Acumatica ERP site.
    -   The test opens the Repair Work Orders \(RS301000\) form.
    -   The test opens the *000001* repair work order.
    -   The test enters *0* in the **Quantity** column for the single line item on the **Labor** tab, and that the quantity value is restored to *1*.
    -   The test saves the record and refreshes the form.
    -   The test completes successfully.
6.  If the test fails and your Visual Studio version provides Copilot menu commands for failed tests, use **Explain failure with Copilot** command before manually pasting log output. If **Debug with Copilot** is available, you may use it as a troubleshooting path. Do not ask Copilot to edit files until you’ve classified the failure.

## Step 4: Reviewing the Passing Output

In this step, you'll review the sanitized passing artifact and confirm that it describes the behavior that you validated in the previous step. Do the following:

1.  Open the prepared passing artifact located in the following path of the `AIAssistedDiagnostics.ModernUI.Tests` project: `artifacts\passing\modern-ui-testsdk-passing-output.txt`.
2.  Confirm that its contents \(shown below\) describe the validated behavior that you observed in the previous step.

    ```
    Open screen: RS301000
    Type into input: Order Nbr., value: 000001
    Type into input: Quantity, value: 0
    Click toolbar button: Save
    Click toolbar button: Refresh
    Expected final quantity: 1
    Observed final quantity: 1
    Exit code: 0
    ```


## Step 5: Reviewing a Prepared Failure Artifact

In this step, you'll review a prepared artifact of Test SDK failure. The purpose of this step is to practice log interpretation even if the smoke and UI tests from Steps 2 and 3 pass. The prepared log gives you a controlled failure artifact that you can use to identify the first useful error message and classify the likely cause.

Do the following:

1.  Open one of the failure artifacts from the `artifacts\failures\` path of the `AIAssistedDiagnostics.ModernUI.Tests` project.
2.  Identify the first useful error message.
3.  Determine whether the failure appears to be caused by one of the following:
    -   A wrapper/member mismatch
    -   A test data issue
    -   A timing or wait issue
    -   A validation not triggered
    -   An environment or configuration issue
    -   An application behavior issue
4.  Record your initial classification. You can use the format shown in the table below.

    |Log Review Item|Value|
    |---------------|-----|
    |Log artifact|Record the file name.|
    |First useful error message|Record the error message.|
    |Failure category|Record your classification of the failure.|
    |Evidence|Record your reasoning for your classification.|
    |Next diagnostic step|Record what you think your next action should be.|


## Step 6: Asking Copilot to Classify a Failure

In this step, you'll use Copilot to interpret a Test SDK failure without assuming the application is wrong. Do the following:

1.  Use the reusable prompt file `classify-testsdk-failure.prompt.md` if it is available in Copilot Chat. If it is not available, open `Assets\CopilotPrompts\classify-testsdk-failure.prompt.md` and paste the prompt text into Copilot Chat.

    If you are not using the reusable prompt file, use the following prompt. Do not use Agent mode for this step. The goal is to classify the failure and decide the next diagnostic step, not to edit files automatically.

    ```
    Review this TestSDK Test failure.
    
    Context:
    - The test uses generated Modern UI Test SDK wrappers.
    - The target screen is Repair Work Orders (RS301000).
    - The test is intended to validate the UI behavior for RSSVWorkOrderLabor.Quantity.
    - The related Unit Test Framework test now passes.
    - Expected UI behavior: after entering quantity 0 for a labor line whose 
      configured/default quantity is 1, validation restores the quantity to 1.
      If supported by wrappers, the QuantityTooSmall warning should also be visible.
    
    Test goal:
    Verify that the UI workflow reflects the repaired labor quantity validation behavior.
    
    Relevant test code:
    [Reference the test method or paste the method if needed.]
    
    Relevant wrapper/helper members:
    - `RepairWorkOrdersScreen`
    - `WorkOrders_fsColumnAOrder.OrderNbr`
    - `Labor_gridLabor.Row.Quantity`
    - `Save()`
    - `Labor_gridLabor.Refresh()`
    
    Failure output:
    [Paste the cleaned failure message, log excerpt, or screenshot description.]
    
    Please classify the likely cause:
    1. Wrapper/member mismatch
    2. Test data issue
    3. Timing/wait issue
    4. Validation not triggered by the test
    5. Application behavior issue
    6. Environment/configuration issue
    
    For each likely cause, suggest the next diagnostic step.
    
    Do not modify files.
    Do not assume the application is defective unless the evidence supports it.
    Do not invent wrapper members or unsupported APIs.
    ```

2.  Compare Copilot’s classification with your initial classification from Step 5.
3.  If they differ, review the evidence and decide which classification is better supported.
4.  Record the final classification and next diagnostic step.

In this activity, you have reviewed and validated a UI test for the labor quantity restoration scenario, analyzed a failure artifact, and used Copilot to classify failure evidence.
